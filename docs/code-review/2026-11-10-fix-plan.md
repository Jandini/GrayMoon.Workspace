# Fix plan for the 2026-11-10 code review

Companion to [2026-11-10-code-review.md](2026-11-10-code-review.md). Finding numbers (#1 to #33) and the P3 bullets refer to that document. Paths are relative to `C:\Workspace\GrayMoon`; App paths are under `GrayMoon/src/GrayMoon.App/`.

The plan has two goals: close every finding in the review, and remove the patterns behind them (section 2 of the review) so they do not come back. It is cut into **work streams that touch disjoint files**, so any number of them can run at the same time, each in its own GrayMoon Feature (worktree) and its own pull request per repository.

## 1. Ground rules for every stream

- **One Feature per stream.** Create a GrayMoon Feature named after the stream (for example `fix-connector-refresh`), work only inside that worktree, run git per sub-repo there. Streams that only touch `GrayMoon/` need a `GrayMoon.Desktop` branch only for the README bullet (see below).
- **Stay inside the stream's file list.** The file lists in section 3 are the contract that keeps streams merge-free. If a fix needs a file owned by another stream, do the smallest compatible change and record it in section 4 (shared files).
- **Confirm before fixing.** Items marked PLAUSIBLE in the review (#5, #19, #23, #29, #30, #32, first half of #33) get a breakpoint or a failing test first. If that shows the code is fine, close the item in the review with one line and move on.
- **Every fix ships with a regression test** that fails on the current code. App tests use `CreateSchemaAsync` and `ManualClock`; Worker git tests start from `GitScenarios`; see `GrayMoon/CLAUDE.md`.
- **Definition of done per stream:** both solutions build with 0 warnings; the three GrayMoon test projects and the Desktop tests pass; the architecture doc that describes the changed behavior is updated in the same change; one bullet per user-visible change at the top of `## Recent GrayMoon changes` in `GrayMoon.Desktop/README.md` (style in `.cursor/rules/update-desktop-readme.mdc`); the finding's row in the review is updated to `Fixed (<branch>)`.
- **Conventions:** CRLF, ASCII hyphens only, `sealed` classes, primary constructors, Worker DTOs as sealed classes with `[JsonPropertyName]`.
- **Never commit or push** unless asked in the current message. Each stream leaves its changes for review.

### J. Guardrails (improve GrayMoon so the patterns do not return)

Files: new tests under `GrayMoon.App.Tests/Conventions/` and `GrayMoon.Worker.Tests/Conventions/`, `Program.cs` (validation flags). These lock in the section 2 patterns of the review:

1. **Event subscriptions are removed.** Source-scan test over `Components/**`: every `+=` or `OnStateChanged(` against an injected singleton has a matching removal in `Dispose`.
2. **Context captured at queue time.** Source-scan test: `RequireSelectedContextId()` never appears inside a lambda passed to `StartJob`, `StartWorkspaceJob` or `ScopedExecutor.ExecuteAsync`.
3. **Page state only on the dispatcher.** Source-scan test: inside job lambdas, assignments to the page's collection fields (`_slots`, `_linkByRepoId`, `prByRepositoryId`, `repoSyncStatus`) appear only inside `InvokeAsync` or `SafeInvoke`.
4. **No per-circuit state in singletons.** `ValidateScopes` and `ValidateOnBuild` on in Development and in a startup test; an allowlist test that every UI notification service like `IToastService` is scoped.
5. **Feature-context writes.** A convention test that the `WorkspaceRepositoryLink` setters for `BranchHasUpstream`, `BranchName` and `CheckedOutTag` are referenced only from the state writer, the link repository and the sync paths named in `06`.
6. **Worker paths are validated.** Convention test: every request DTO property named `*Path` or `*Paths` is consumed through `GitRepositoryPathValidator` (allowlist for the few that are not filesystem paths).
7. **Best-effort steps report.** Grep-level test that no `catch (Exception)` in `Services/Workspaces` and `Services/Git` swallows without logging and returning an outcome.

Each scan starts with an explicit exception list containing today's violations if J is written before the streams land, and the list shrinks to empty as they merge.

### K. Close-out

Runs once every other stream has merged. The review and this plan are working documents for the fix effort, not part of the repository's lasting documentation: when the work is done they are deleted, and what they taught goes into the standing rules and the architecture docs in their own words.

1. **Verify nothing is left.** Every finding row in the review reads `Fixed (<branch>)` or `Closed: not reproducible (<note>)`, and the section 5 "Left as documented intent" items are all fixed. Any row still open goes back to its stream before this step continues. The same holds for [2026-11-10-follow-up.md](2026-11-10-follow-up.md): every `N` item reads Fixed or Moved (to a `GrayMoon/docs/todo/defects/` note), and its section 3 list is empty. Open today: #33 and N9 (move the signing secrets, record the two workflow runs), and the section 3 items (#5 manual check, #17 and #23 tests, #21 known gaps, the review section 5 sentence).
2. **Fold the lessons into the rules.** Update `GrayMoon/CLAUDE.md`, `GrayMoon/AGENTS.md`, `GrayMoon.Desktop/CLAUDE.md` and the `.cursor/rules/*.mdc` files with the standing rules the fixes established, written as plain rules of the codebase:
   - Feature contexts write `WorkspaceRepositoryContextState` only, and only through the state writer; shared `WorkspaceRepositories` columns are never written from a Feature context.
   - Page jobs load off the dispatcher and apply on it (`InvokeAsync` or `SafeInvoke`); page collections are never swapped from a job body.
   - The context id and generation are captured before a job is queued, never read inside the job body.
   - No singleton holds per-circuit state or component handlers; every subscription on a singleton is removed in `Dispose`; `ValidateScopes` and `ValidateOnBuild` stay on.

## 6. Open questions with recommended answers

All five recommendations were agreed on 2026-11-10; the streams proceed on them. The questions stay here as the record of why.

### Q1. Docker Origin policy for #7 (stream E)

**Feature:** Docker deployment of GrayMoon.App used from a browser on the LAN; the REST API under `/api/...` and the connector endpoints that hold GitHub tokens.

Today `RequestSecurityMiddleware` accepts an Origin whose host equals the request Host, and Docker mode ships `AllowedHosts "*"`, so a DNS-rebinding page can reach `/api/...`.

- **Recommended:** accept an Origin only when its host is loopback or listed in `GRAYMOON_AllowedHosts`. When the list is empty, log one startup warning and accept loopback only. The Docker README and the wiki Docker page document the variable as required for LAN use.
- Alternative: keep the current rule and only move the PAT endpoint (`GET /repos/{id}/connector`) behind the Worker secret.
- Why the recommendation: Desktop mode already relies on `GRAYMOON_AllowedHosts`, so Docker gets the same mechanism instead of a second one, and the fix closes the whole API surface rather than one endpoint. The cost is one environment variable for LAN users, which the startup warning points at.
- **What improves:** a GrayMoon container on a shared network can no longer be driven by a web page the developer happens to open, and a stored GitHub token cannot be read that way. Docker and Desktop follow one host rule, so the security section of the docs describes one behavior. Nothing changes for a container used from the same machine.

Answer: Agreed on 2026-11-10. Loopback plus `GRAYMOON_AllowedHosts`; empty list means loopback only with a startup warning.

### Q2. Worker secret required by default (stream E, P3)

**Feature:** Worker pairing (the Worker page, `graymoon-worker install`, the `/hub/worker` SignalR hub) and the connector endpoints the Worker calls to fetch tokens for git.

The secret is optional until the first pairing, so a Docker App that has never paired a Worker accepts any Worker and serves connector tokens without a secret.

- **Recommended:** flip the default to required in this release. When no secret exists the App generates one at startup and shows it on the Worker page as the first-pairing step; the Worker install copies it as today. Existing installs without a secret see the Worker page instruction, not silently open endpoints. Needs one wiki note and a Desktop README bullet.
- Alternative: keep it optional and add a warning banner on the Worker page.
- Why the recommendation: the open window is exactly the moment an attacker on the LAN would use, and the pairing surface already exists, so the change is small. The banner alternative leaves the window open for anyone who ignores it.
- **What improves:** only a Worker the developer paired can run git on their machine or receive their tokens, from the first start onward, with no "secure it later" step to forget. The Worker page becomes the one place that explains pairing, so a fresh Docker install has a clear first action instead of a silently open hub. Desktop installs, which already pair during Install All, see no difference.

Answer: Agreed on 2026-11-10. Required by default; the App generates the secret and shows it on the Worker page for first pairing.

### Q3. Remove Feature when a repository became dirty after analysis (stream H, #18)

**Feature:** Remove Feature on the Repositories page: the analysis dialog that lists uncommitted work per repository, the "discard uncommitted" choice, and the queued removal that deletes worktrees and the Feature folder.

Remove sends `force = AllowDiscardUncommitted` to every repository at execution time, so a repository that was clean at analysis and dirty when the queued removal runs is force-removed without a warning.

- **Recommended:** re-probe each repository when the queued removal starts. A repository that became dirty since the check is skipped with "changed since the check, run Remove again"; the other repositories proceed. The Feature stays in a partly removed state that the existing Remove flow already handles.
- Alternative: honor the original `AllowDiscardUncommitted` choice (today's behavior) and only log a warning.
- Why the recommendation: the user approved discarding what they saw in the analysis dialog, not changes made afterwards; the removal runs unattended, so there is nobody to re-ask. Skipping is safe and reversible, force is not.
- **What improves:** work saved in a Feature worktree between clicking Remove and the removal actually running (an editor autosave, a build output, a last commit from another window) is never deleted without being shown first. The Remove dialog's list of what will be discarded becomes a promise, not a snapshot. Removal of clean repositories is as fast as today.

Answer: Agreed on 2026-11-10. Re-probe at execution; a repository that became dirty is skipped with "changed since the check, run Remove again".

### Q4. Actions idle-tier polling: fix the layout mount or rewrite doc 04 section 14 (stream D)

**Feature:** the Actions page (GitHub Actions workflow runs per repository) and its background refresh, which polls GitHub while the page is open and is meant to slow down when the browser tab or Desktop window is idle.

Doc 04 section 14 says the Actions page drops to an idle polling tier when the browser is inactive. `WorkerConnectionTracker` is mounted in the static layout, so the idle tier never runs and the page polls at the active rate all the time.

- **Recommended:** fix the mount. Move the tracker subscription into the interactive layout so the idle tier works as documented, and keep section 14 as it is.
- Alternative: rewrite section 14 to say the Actions page polls at one rate and remove the idle-tier wording.
- Why the recommendation: the idle tier was designed to cut GitHub API calls from background tabs, and the review found the only reason it does not work is the mount. Stream D is already in `MainLayout.razor` for #3, so the fix is in the same file and the same change.
- **What improves:** an Actions tab left open in the background stops spending the GitHub rate limit at the active rate, so Sync, pull request refresh and the Repositories page are less likely to hit "rate limited" during a long session with several tabs. The page still refreshes at full speed the moment the user comes back. The fix also makes the shipped behavior match the architecture doc, so the next person reading section 14 is not misled.

Answer: Agreed on 2026-11-10. Fix the mount in the interactive layout; doc 04 section 14 stays as written.

### Q5. How a Desktop release pins the bundled App version (stream G2, #33)

**Feature:** the GrayMoon.Desktop release pipeline (the `release.yml` workflow that bundles GrayMoon.App into the Desktop installer) and Desktop auto-update through Velopack, which delivers that bundle to users.

A stable Desktop tag resolves GrayMoon to `releases/latest` at run time, so re-running the same Desktop tag later can bundle different App code.

- **Recommended:** a version file in the Desktop repo (for example `build/graymoon-app-version.txt` holding the App tag). The release workflow reads it, downloads that exact App release, and fails when the tag does not exist. Bumping the App in Desktop becomes a one-line commit that the Desktop tag then records.
- Alternative: require the App tag as a `workflow_dispatch` input and refuse tag pushes without it.
- Why the recommendation: a file is reviewed in the pull request, visible in `git log`, and reproducible from the tag alone; a dispatch input is typed by hand and is not recorded by the tag. The file also gives the Desktop README a single place to show which App version a Desktop release contains.
- **What improves:** every Desktop version maps to exactly one App build, so a bug report that names a Desktop version names the App code too, and a re-run of an old tag reproduces the same installer. Users who auto-update get the App version the release notes describe, never a newer one that slipped in because it was published first. The release notes and the About dialog can state the bundled App version from the same file.

Answer: Agreed on 2026-11-10. A version file in the Desktop repo holding the App tag; the release workflow reads it and fails on an unknown tag.
